# Effects on parts and outputs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Smart Q's EQ, Dynamic, De-Ess, Width and Transient on each part of each song (up to 4, before the fader), and EQ, Dynamic, Limit and Width on each output (up to 4, after its mix), heard live in Edit mode and prepared in advance for Show mode, so the stage plays finished audio from memory.

**Architecture:** Smart Q's DSP (`smartq::dsp`, plain C++) is copied into `src/dsp` as its own library and wrapped by one engine class, `EffectChain`, around Smart Q's `dsp::Chain`. The model gains `EffectDoc` lists on parts and outputs, with commands. The engine runs part chains live inside `SongRenderer` only when given them (Edit mode), and output chains after the mix in every mode, with each output delayed to the slowest. Offline, `applyEffects` runs a part through its chain from its first sample; a per-computer `PreparedStore` keeps the results on disk, and the song cache plays them in Show mode. The UI reuses Smart Q's module pages behind a stand-in for the plugin, in a new effects window, opened from an Effects box on every mixer strip and a new output strip.

**Tech Stack:** C++20, JUCE 9.0.4, Catch2, CMake; Windows first.

**Spec:** `docs/superpowers/specs/2026-11-22-effects-design.md` (read it whole; it is the authority). Mockup: `docs/mockups/effects.html` (frames `#mixer`, `#chain`, `#output`; the `rack()` and `strip()` functions and `SETS` hold the visual details). Smart Q source: `D:\development\smarteq_vst` (`src/dsp`, `src/ui`, `src/plugin`).

## Global Constraints

- **Start only after the mixer console plan (`docs/superpowers/plans/2026-11-22-mixer-console.md`) is finished and pushed.** Tasks 11 and 12 change `ChannelStrip`, `MixerPanel`, `MixerState` and `MixerPage`, which that plan is still changing.
- Build and test: `powershell -File scripts/build.ps1 -Test "<filter>"`; the whole suite: `-Test "~[benchmark]"`; the app: `-Target SmartQLive`; screenshots: `Start-Process -Wait -WorkingDirectory (Get-Location) -FilePath "build\SmartQLive_artefacts\Release\Smart Q Live.exe" -ArgumentList '--screenshots','build\screens'`. No Node or Python on this PC.
- **Audio thread:** never allocates, locks, waits or frees. Output is bit-identical at any block size. Use `tests/support/AllocGuard.h` around `process` in the engine tests.
- **No effects means no change:** a song whose parts have no effects, on a rig whose outputs have none, renders bit for bit as before. Every existing engine, level-check and session test passes unchanged.
- **Subsets:** parts take `eq`, `dynamic`, `deess`, `width` (stereo parts only), `transient`; outputs take `eq`, `dynamic`, `limit` (at most one per output), `width` (stereo outputs only). At most 4 effects per chain.
- **Delay:** part effects add none. Dynamic's lookahead is held at 0 on parts and on outputs; Limit's lookahead is at most 5 ms (its own maximum), so an output chain's delay stays under about 9 ms at 48 kHz (Limit: lookahead + 42 samples with True Peak + 131 with Soft Clip).
- **JSON:** `PartDoc` and `OutputDoc` gain `"effects"`: an ordered array of `{"kind": "eq"|"dynamic"|"deess"|"width"|"transient"|"limit", "on": bool, ...settings}`. A setting's key is Smart Q's parameter field name (the `<field>` of `<slotId>_<field>` in `smarteq_vst/src/plugin/Parameters.cpp:275`, for example `"threshold"`, `"true_peak"`); EQ bands are `"bands": [{"shape", "freq", "gain", "q", ...}]` with the field names Smart Q uses for `eq1_band01_<field>`. Absent = none. Old files load; unknown keys stay in `extra`; an unknown kind is kept but not played.
- **Show mode never writes the band folder** (the CommandLayer guard), and no effects window opens there.
- **Prepared audio never goes in the band folder.** It lives in the per-computer folder `PreparedStore::defaultFolder()` (next to the settings file: `<settings folder>/Prepared audio`).
- Meaning colours (`model/MeaningColours.h`): mint = on, ready; caution amber = changed, "will be prepared again", a limiter working hard; danger red = mute, over 0 dB.
- Copied Smart Q code keeps its namespace (`smartq::dsp`) and its `"dsp/X.h"` includes. It uses SSE2 (`Svf.h`, `MatchMeter.cpp`), which is fine on Windows x64; the Mac build (later) will need a portable fallback: note it in `THIRD_PARTY.md`, change nothing now.
- Files are split once past about 800 lines.
- Commit and push to `origin main` after each task (the user's standing request), staging only that task's files by path. Messages end with the implementer model's `Co-Authored-By` line.

## Review Focus

1. **Edit mode and Show mode must agree.** A song with effects, started from its start, with a count-in and audio before bar 1, must give exactly the same output live (Edit) as prepared (Show) up to its first jump. The live chain must be fed from the part's sample 0, never from the count-in's silence (Task 5 test).
2. **Stale prepared audio:** a part's file replaced with new audio under the same name, an effect changed, or the sample rate changed must never play the old prepared audio. A store emptied with "Clear" while songs are loaded is prepared again, not an error (Task 7 tests).
3. **A failed write** (a full disk, a read-only store folder) must not stop a show: the prepared audio is still used from memory, and the pre-show check says the store couldn't be written (Task 7 test).
4. **A device change** (a new rate or buffer size) while chains are set: chains are rebuilt for the new device and nothing on the audio thread allocates (Task 8 test).
5. **Fast knob moves while playing in Edit mode:** no allocation, no rebuilt chain (so no reset) for a settings-only change, and undo heard at once. In Show mode no effects command passes the guard (Task 8 test).
